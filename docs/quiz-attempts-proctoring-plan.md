# Попытки прохождения теста и прокторинг — план

Рабочий документ по итогам обсуждения. Не реализовано — это зафиксированные решения
и открытые вопросы, чтобы к ним можно было вернуться.

Статус: обсуждение завершено, к реализации не приступали.

---

## Контекст: как тест проходит на самом деле

Это очный тест в аудитории, а не удалённая сдача. Отсюда следуют почти все решения ниже.

- Студенты физически приходят в аудиторию и садятся за университетские ПК.
- **Ответственный** (администратор / преподаватель) активирует тест. Студент активировать тест не может.
- Ответственный **объявляет PIN вслух всей аудитории**.
- Если у студента возникает проблема, её решает ответственный, находящийся в комнате.
- Компьютеры — университетские, **Chrome на ПК**. Телефоны — не основной сценарий.
- **Веб-камера есть не на всех ПК**, поэтому прокторинг по лицу — опция для части студентов,
  а не режим по умолчанию.

Два следствия, которые важнее всего:

1. **PIN внутри аудитории публичный по определению.** Он не может ограничивать повторные
   попытки — студент его знает и сидит в этой же комнате. PIN защищает только от посторонних снаружи.
2. **Компьютеры наши.** Значит доступны средства управления браузером, которых нет
   у систем удалённого прокторинга. Это сильнее любой защиты на JavaScript.

### Внимание: есть второй сценарий — онлайн-обучение

Этот документ описывает **очный тест в аудитории**. Прокторинг по лицу используется в другом
сценарии — для **студентов онлайн-обучения**, где в группе 50 человек и больше.

Для них **не работает** значительная часть решений ниже:

| Решение из этого документа | Онлайн |
|---|---|
| Киоск-режим Chrome, политики `DeveloperToolsAvailability` | **Неприменимо** — компьютеры чужие |
| Ответственный решает проблему на месте | **Никого нет рядом** |
| Человек в комнате видит нарушение глазами | **Только прокторинг** |

Что для онлайн-студентов остаётся: heartbeat, события браузера, экран мониторинга (но смотреть
на него нужно удалённо), возобновление попыток, лимит попыток. И главное — прокторинг по лицу
становится **единственной** линией обороны, поэтому клиентский флаг `cheating_detected`
(см. последний раздел) для них означает отсутствие надзора как такового.

Производительность и переход прокторинга на HTTP разобраны отдельно:
[face-detection-scaling-plan.md](face-detection-scaling-plan.md).

## Проблема, с которой начали

`start_quiz` не проверяет, есть ли у студента уже открытая или завершённая попытка
(`backend/app/modules/quiz/quiz_process/repository.py`). Знаешь PIN — стартуй сколько хочешь
и оставь лучший результат.

`repeat_quiz` в роутере решает другую задачу — клонирование квиза преподавателем.

### Почему нельзя просто запретить вторую попытку

Запрет «есть Result → 403» сломает то, что в аудитории происходит постоянно:

- завис ПК, пропал свет, упал браузер, студент нажал F5;
- ложное срабатывание прокторинга (кто-то прошёл за спиной);
- студента пересадили за другой компьютер.

**Настоящая задача — отличить возобновление прерванной попытки от новой попытки ради оценки.**
Всё решение строится вокруг этого различия.

## Принятые решения

### 1. Возобновление вместо новой попытки — фундамент

При существующей `in_progress` попытке `start_quiz` не создаёт вторую, а возвращает ту же:
те же вопросы, уже данные ответы, оставшееся время.

Новых полей не требуется — всё уже есть:

- вопросы попытки зафиксированы: строки `UserAnswers` резервируются при старте;
- время старта — `Result.created_at` (в модели это прямо задокументировано).

Оставшееся время = `duration − (now − created_at)`, считается на сервере.

**Побочный эффект — закрывается отдельная дыра:** сейчас таймер живёт на клиенте, сервер отдаёт
`duration`, браузер отсчитывает сам. Перезагрузил страницу — получил свежие 60 минут.
Отсчёт от `created_at` это устраняет.

**Важно:** возобновление должно проверяться **до** проверки PIN и `is_active` (см. решение 3),
иначе студент со сбоем не сможет вернуться после закрытия входа.

### 2. Автозакрытие зависших попыток — обязательное дополнение к пункту 1

Сегодня студент, закрывший ноутбук, оставляет `Result` в `in_progress` навсегда. С правилом
«есть открытая попытка → возобновляем» такой студент окажется заперт в мёртвой попытке
с истёкшим временем: ни продолжить, ни начать заново.

Правило: попытка старше `created_at + duration + запас` считается истёкшей и закрывается
по фактически данным ответам.

Открыто: лениво (при следующем обращении) или фоновой задачей. Ленивый вариант проще
и не требует планировщика.

Заодно чинит отчётность — сейчас брошенные попытки навсегда висят как «в процессе».

### 3. Смена PIN при деактивации — идея принята

Предложение: при деактивации квиза генерируется новый PIN. Объявленный вслух код умирает
в момент закрытия теста, вечером из общежития по нему не зайти.

Это даёт «окно активности» без полей `started_at` / `ends_at`: окно = период между активацией
и деактивацией.

Оговорки:

- `is_active` и PIN сейчас проверяются только на входе; `submit_answer` и `end_quiz` их не смотрят.
  То есть деактивация = «закрыть вход», уже пишущие дописывают спокойно. Это удобно и правильно,
  но сейчас получилось случайно — **зафиксировать как осознанное правило**.
- **Возобновление должно обходить проверку PIN и `is_active`.** Студент с открытой попыткой уже
  внутри, повторно пускать его не нужно. Без этого закрытие входа запрёт снаружи всех, у кого сбой.
- 4-значного PIN в этой связке достаточно: перебор требует валидного студенческого аккаунта,
  отсекается проверкой группы, ограничен окном и rate limit. Проблемой был **неменяющийся** PIN.
- PIN **не ограничивает повторные попытки внутри аудитории** — см. контекст.

### 4. Счётчик попыток — идея принята с исправлениями

**Считать по `Result`, а не отдельным полем.** `Result` — это уже строка «попытка студента X
по квизу Y». Количество попыток = `COUNT(*)` по `user_id + quiz_id`. Ноль новых полей.

Причина: денормализованный счётчик **всегда** рассинхронизируется с реальностью — удалили
ошибочный результат, откатилась транзакция, аннулировали попытку. Дальше начинается
«почему студент не может зайти». Считаемое по факту значение соврать не может.

**Лимит хранить на квизе, не на студенте.** Это свойство правил теста: экзамен — 1 попытка,
тренировочный — 5. Поле на `Student`/`User` неверно: за семестр студент проходит десятки тестов.

**Обязательное условие: возобновление не тратит попытку.** Без него лимит работает наоборот нужного:

- у честного студента завис ПК → попытка сгорела ни за что;
- хитрый студент проходит попытку №1 «на разведку» (посмотреть вопросы) и заходит по №2 подготовленным.

То есть в чистом виде лимит наказывает пострадавшего и награждает жулика. В связке
с возобновлением — сбой не стоит ничего, «разведка» стоит попытку.

Роль лимита — **страховка** («больше 3 попыток — стоп, разбирайтесь вручную»), а не основной механизм.

### 5. Защита от гонки на уровне БД

Проверки в коде мало: два одновременных `start_quiz` (двойной клик, два таба) оба пройдут
проверку и создадут два `Result`.

Нужен частичный уникальный индекс — одна `in_progress` попытка на пару студент+квиз.
Приём в проекте уже применяется: частичный уникальный индекс на `(external_source, external_id)`
в `backend/app/core/mixins/external_ref.py`.

### 6. Экран ответственного — ядро всей схемы

Сейчас у ответственного **нет инструмента**. Он может только деактивировать квиз (действует
на всех 25 человек) или клонировать его через `repeat_quiz` (снова на всю группу). Вернуть
одного студента в его попытку он не может. «Ответственный решит проблему» — сегодня это
намерение, а не возможность.

Разделение труда:

- **человек решает**, была ли причина уважительной — этого не увидит никакая программа;
- **система исполняет** решение точно, адресно и с записью в журнал.

Экран «идёт тестирование» со списком студентов квиза и живым состоянием:

| Студент | Состояние |
|---|---|
| Азиз | прервался, 12 из 30 ответов, осталось 24 мин |
| Дилноза | пишет, осталось 31 мин |
| Санжар | сдал, оценка 4 |
| Нодира | не заходил |

Действия напротив каждого: **вернуть в тест**, **дать новую попытку**, **завершить принудительно**.

Точечный допуск должен быть **одноразовым**: привязан к паре студент+квиз, сгорает при входе.
Иначе «открыл Азизу» превращается в постоянно открытую дверь.

Побочная польза: ответственный видит, что Санжар уже сдал, и его повторный заход заметен
сразу, а не всплывает в отчёте через неделю.

### 7. «Завершить» — это два разных действия, а не одно

За словом «завершить» прячутся две операции с **противоположными последствиями для студента**:

| Действие | Что происходит | Когда |
|---|---|---|
| **Завершить принудительно** | Попытка закрыта, оценка по данным ответам (12 из 30 → двойка) | Нарушение; время вышло |
| **Аннулировать и дать новую** | Попытка недействительна, оценка не выставляется, студент заходит заново | Технический сбой, ложное срабатывание |

Должны быть **две разные кнопки** с разными формулировками. Одна кнопка «завершить» приведёт
к тому, что ответственный в спешке выдаст двойку за поломку техники.

Обе операции обязаны записывать **кто** нажал и **почему**. Поле `reason_for_stop` в `Result`
уже существует (сейчас используется только прокторингом) и подходит для этого.

## Обнаружение проблем во время теста

Сегодня бэкенд не знает про студента **ничего** между стартом и финишем. Проверено:
heartbeat нет, событий браузера на странице теста нет, канала «face-service → backend» нет
(face-сервис ходит по HTTP только за эталонной картинкой).

### Источники сигнала

**1. Heartbeat — основа.** Браузер раз в 20–30 секунд стучится на бэкенд: «жив, на вопросе 12 из 30».
Нет стука дольше минуты — студент отвалился. Работает в любом режиме.

Поскольку камера есть не у всех, **для большинства студентов heartbeat будет единственным
источником данных**.

**2. Разрыв WebSocket прокторинга — бесплатный сигнал, который сейчас выбрасывается.**
Face-сервис уже точно знает момент закрытия браузера, но просто пишет строку в лог
(`face-detection/app/api/v1/stream.py`). Нужен канал «face-service → backend», которого нет.
Работает только при `proctoring_mode = "face"`.

**3. Время последнего ответа — ничего делать не надо.** `UserAnswers.updated_at` уже пишется.
Сигнал слабый и медленный, но бесплатный.

### Чего мы принципиально не сможем

Отличить «завис компьютер» от «студент выдернул кабель, поняв, что проваливает тест» —
технически это **одно и то же событие**.

Отсюда правило: **система показывает факт, а не диагноз.** Не «у Азиза проблема с браузером»,
а «Азиз не выходит на связь 2 минуты, ответил на 12 из 30, осталось 24 минуты». Решает человек.

### Не смешивать живость и состояние попытки

- **Живость связи** (активен / потерял связь) — меняется каждые 30 секунд, эфемерна,
  через час никому не нужна → **Redis с TTL** (ключ протухнет сам; в проекте уже есть
  такой паттерн для сессий).
- **Состояние попытки** (пишет / сдал / прерван / аннулирован) — бизнес-факт, нужен
  в отчётах через полгода → **БД, `Result.status`**.

Если свалить в одно поле, получится запись в Postgres на каждого студента каждые 30 секунд
ради данных, протухающих через минуту.

### Нагрузка

200 студентов × раз в 30 сек ≈ 7 запросов/сек. Немного, но каждый пройдёт через
`PermissionRequired`, а это **три обращения к БД** (`backend/app/core/dependencies/role_checker.py`)
— около 20 запросов к Postgres в секунду просто на «я жив».

Heartbeat делать лёгким сразу: писать в Redis, не гонять через тяжёлую проверку прав.

## События браузера

### Чем что ловится

| Событие | API | Ловит | Не ловит |
|---|---|---|---|
| Переключение вкладки, сворачивание | `visibilitychange` + `document.visibilityState` | Вкладку, сворачивание, блокировку экрана | Другое окно поверх видимого браузера |
| Потеря фокуса | `blur` / `focus` на окне | Клик по другому приложению | — (шумный: адресная строка, уведомления) |
| Уход со страницы | `pagehide` (надёжнее), `beforeunload` | Закрытие вкладки, переход | Выключение питания, обрыв сети, зависание |
| Полный экран | `fullscreenchange`, `document.fullscreenElement` | Выход по Esc / F11 | — |

Трактовать `visibilitychange` как весомый сигнал, `blur` — как слабый намёк.

### Технические детали, на которых спотыкаются

- **`navigator.sendBeacon()` для ухода со страницы.** Обычным запросом сообщить серверу об уходе
  нельзя — страница умрёт раньше, чем запрос уйдёт. `sendBeacon` специально сделан, чтобы браузер
  доставил пакет уже после закрытия вкладки.
- **Полный экран включается только по жесту пользователя**, автоматически при загрузке — нельзя.
  Нужен экран «Начать тест» с кнопкой: по этому клику одновременно стартует попытка
  и включается полноэкранный режим.
- **Выход по Esc / F11 запретить нельзя** обычными средствами — браузер это гарантирует
  пользователю (но см. Keyboard Lock ниже).

### Ключевая идея: состояние внутри heartbeat, а не только события

Отдельные события легко потерять: сеть моргнула, обработчик отключили. Раз браузер и так
стучится каждые 20–30 секунд, пусть **каждый стук несёт текущее состояние**: в фокусе ли окно,
включён ли полный экран, на каком вопросе студент, сколько нарушений накопилось.

Что это даёт:

- потерянный пакет не теряет информацию — следующий принесёт то же состояние;
- чтобы скрыть переключение вкладки, надо подделывать постоянный поток, а не одно событие;
- разрывы самого потока видны сами по себе.

Отдельные события остаются — они дают точное время и длительность. Но опора — поток.

### Правила трактовки

1. **Считать, а не блокировать.** Не «переключил вкладку → тест закрыт»: ложных срабатываний
   будет много (уведомление, случайный Alt+Tab). Лучше счётчик с порогом и **видимое
   предупреждение студенту**: «вы покинули страницу теста, это зафиксировано; осталось
   2 предупреждения». Предупреждение работает лучше запрета — студент знает, что его видят.
2. **Длительность важнее факта.** Ушёл на 1 секунду и на 3 минуты — разные вещи, событие одно.
   Фиксировать интервал (ушёл 14:32:10, вернулся 14:35:40), иначе журнал = сорок одинаковых строк.
3. **Это свидетельство, а не приговор.** Всё живёт в браузере, браузером управляет студент.
   События идут в журнал и на экран ответственного, решение принимает человек.

## Chrome на университетских ПК — самый сильный слой

Всё перечисленное выше живёт в браузере и обходится через DevTools за 10 секунд.
Но компьютеры в аудитории — **ваши**, и это даёт рычаг, которого нет у удалённого прокторинга.

### Киоск-режим — ноль кода

```
"C:\Program Files\Google\Chrome\Application\chrome.exe" --kiosk "https://example.com"
```

Ярлык на рабочем столе, которым ответственный запускает тест. Нет адресной строки,
нет вкладок, нет доступа к другим сайтам. Не требует от разработчика ничего.

### Политики Chrome — самое ценное

Если машины в домене или подключены к Chrome Browser Cloud Management, администратор задаёт
политики централизованно. Главная — **`DeveloperToolsAvailability` в положении «запрещено»**.

Это убирает DevTools полностью, а вместе с ними — основной способ обойти любую клиентскую
защиту. Ни один JS-приём такого не даст: надёжно **обнаружить** открытые DevTools нельзя,
но можно сделать так, чтобы их не было.

**Требует отдельного разговора с администратором компьютеров в аудиториях.** По эффекту
сопоставимо со всем списком разработки вместе взятым, а кода не требует.

### Что открывает Chrome на ПК со стороны кода

**Keyboard Lock** (`navigator.keyboard.lock()`) — только Chrome, работает **исключительно
в полноэкранном режиме и только по HTTPS**. Перехватывает браузерные комбинации: Escape, F11,
Ctrl+W, Ctrl+T, Ctrl+N.

Не перехватывает системные — **Alt+Tab на Windows, клавишу Win**: их забирает ОС раньше браузера.
Они ловятся только через потерю фокуса. Связка «киоск + Keyboard Lock» закрывает почти всё,
что делается внутри браузера.

**Screen Wake Lock** — не защита, а устранение ложных срабатываний, и оно понадобится.
Студент читает длинный вопрос пять минут не трогая мышь → энергосбережение гасит экран →
`visibilitychange` → в журнале «покинул страницу». Wake Lock убирает целый класс таких инцидентов.

**Fullscreen можно требовать жёстко.** Вышел → тест на паузе с экраном «вернитесь
в полноэкранный режим», время продолжает идти. Честнее блокировки, не требует вмешательства
ответственного, факт и длительность остаются в журнале.

### Проверить до начала разработки: HTTPS

**Keyboard Lock, Wake Lock и доступ к камере требуют HTTPS.** Без защищённого соединения они
не работают вообще — не «хуже», а отсутствуют.

Если часть аудиторий заходит по внутреннему адресу вида `http://192.168.x.x:3000`, то там
**уже сейчас не работает камера**, и это, возможно, никто не связал с протоколом.

Нужно выяснить, по какому именно адресу студенты в аудиториях открывают систему. По коду ответ
получить нельзя: прод-конфигурация nginx в репозитории отсутствует (`docker-compose.prod.yml`
удалён коммитом 33c15e1, а `docs/host-nginx-setup.md` ссылается на контейнер `nusmt_nginx`,
которого в репозитории нет).

## Порядок работ

1. **Возобновление попытки + автозакрытие зависших** (решения 1 и 2) — парные, дают больше всего:
   чинят и злоупотребление, и клиентский таймер, и брошенные попытки.
2. **Частичный уникальный индекс** (решение 5) — маленький, но без него первый пункт дырявый.
3. **Heartbeat с состоянием внутри** — основа мониторинга и обнаружения сбоев.
4. **Экран ответственного** (решение 6) + два действия завершения (решение 7).
5. **Смена PIN при деактивации** (решение 3) и **лимит попыток** (решение 4).
6. **События браузера** — точность поверх heartbeat.
7. **Fullscreen + Keyboard Lock + Wake Lock**.

Параллельно и не дожидаясь ничего: **разговор с администратором ПК про киоск-режим
и запрет DevTools**, и **проверка HTTPS в аудиториях**.

## Открытые вопросы

1. **Какие проблемы в аудитории случаются чаще всего?** От этого зависит набор кнопок
   у ответственного. Три разных сценария с разными действиями:
   - техника (завис ПК, свет, интернет) → «вернуть в тест», время желательно не терять;
   - ложное срабатывание прокторинга → снять отметку о нарушении и вернуть;
   - студент опоздал, вход уже закрыт → впустить одного, не открывая вход всем.

2. **Ответственный сидит за своим компьютером или ходит по аудитории?** Если ходит — экран
   мониторинга должен работать на телефоне, и встаёт вопрос, кто смотрит на монитор, пока он
   помогает студенту в дальнем углу.

3. **Что делать, если тест создан с `proctoring_mode = "face"`, а камеры нет или студент отказал
   в доступе?** Сейчас сервер выдаст `face_ws_token`, браузер не подключится, тест пройдёт без
   прокторинга — и в `Result` не останется следа, что прокторинг фактически не работал.
   Через месяц не отличить студента, за которым следили, от студента без камеры.
   Варианты: не пускать; пускать с пометкой «прокторинг не активен» в `Result`; спрашивать
   ответственного. Важно, чтобы это было решением, а не случайностью.

4. **Пересдача нужна на уровне студента или группы?** Если по регламенту пересдаёт вся группа —
   `repeat_quiz` можно оставить. Если типичный случай «у одного сломался компьютер» — нужен
   точечный допуск (решение 6).

5. **Что происходит с прокторингом при срабатывании — закрывать попытку или ставить на паузу
   до решения ответственного?** Сейчас закрывается сразу с оценкой. Раз в комнате сидит человек,
   логичнее приостановить: иначе каждое ложное срабатывание = двойка и разбирательство постфактум.

## Связанная проблема (обсуждалась отдельно, здесь не решается)

Решение о нарушении сейчас принимает браузер и присылает флагом `cheating_detected` в `end_quiz`.
Не подключил WebSocket — прокторинга нет; отправил `false` — нарушения нет. Эталонное лицо
задаётся query-параметром `image_url`, не связанным с подписанным токеном, а при неудаче эталоном
становится первый пойманный кадр.

Это отдельная задача — перенос вердикта на сервер. Здесь не рассматривается, но пересекается
с каналом «face-service → backend» из раздела про обнаружение проблем: канал нужен обеим задачам.

**Решается в [face-detection-scaling-plan.md](face-detection-scaling-plan.md)** — при переходе
прокторинга с WebSocket на HTTP кадр приходит на сервер, и вердикт естественно выносится там же.
Там же зафиксировано, что эту возможность нельзя использовать наполовину, иначе получится новая
архитектура со старой дырой.

Для онлайн-студентов это не «недостаток», а критическая дыра: рядом с ними никого нет,
и решение о нарушении сейчас принимает их собственный браузер.
