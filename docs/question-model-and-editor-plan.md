## Что решено

1. **Номера вариантов вместо текста** — предварительное условие для всего остального.
2. **Адреса картинок хранить относительными** (`/uploads/...`), без домена.
3. **Добавить валидацию загрузки** файлов.
4. **Не удалять картинку сразу при правке вопроса** — версионирование этого не позволяет.
5. **Формулы: добавить MathML**, картинки оставить (сосуществование).

## Часть 1. Как проверяется ответ сейчас

Полный путь одного ответа:

**1. В базе** — шесть колонок (`backend/app/modules/quiz/model.py`):

```
text           = "Столица Узбекистана?"
option_a       = "Ташкент"      ← правильный
option_b       = "Самарканд"
option_c       = "Бухара"
option_d       = "Наманган"
correct_option = "a"
```

**2. При старте теста** варианты перемешиваются (`Question.to_dict`) и раскладываются обратно
по буквам (`quiz_process/repository.py`):

```
option_a = "Бухара"
option_b = "Ташкент"     ← правильный теперь под буквой B
option_c = "Наманган"
option_d = "Самарканд"
```

**3. Студент** видит A/B/C/D и кликает «B».

**4. Браузер** отправляет не букву, а **текст** (`frontend/src/pages/QuizTestPage.tsx`, ~строка 149):

```
{ question_id: 42, answer: "Ташкент" }
```

**5. Сервер** сравнивает две строки (`quiz_process/repository.py`, ~строка 200):

```
is_correct = data.answer == question.get_correct_text()
```

### Корень проблемы: у вариантов нет опознавательного знака

Почему браузер шлёт текст, а не букву? Потому что после перемешивания **буква на экране
не совпадает с буквой в базе**, а перемешивание своё у каждого студента. Сервер не знает,
какой порядок достался этому конкретному студенту.

Больше у варианта ничего нет — ни номера, ни идентификатора, только текст. Поэтому текст стал
единственным способом сказать «я выбрал вот этот».

**Из этого следует всё остальное:** правильность держится на посимвольном совпадении строки,
прошедшей путь база → сервер → сеть → браузер → сеть → сервер.

## Часть 2. Где сравнение по тексту ломается

### Случай 1: два варианта с одинаковым текстом

```
option_a = "0"
option_b = "1"
option_c = "0"      ← опечатка преподавателя
option_d = "-1"
correct_option = "c"
```

Студент выбирает «0», отправляет `"0"`, сервер сравнивает с правильным `"0"` — **совпало**.
На такой вопрос **невозможно ответить неправильно**, и никто об этом не узнает:
статистика покажет, что вопрос лёгкий.

### Случай 2: вопросы с двумя вариантами — встретится гарантированно

Схема требует **все четыре варианта непустыми** (`question/schemas.py`, валидатор
`must_not_be_empty`). Вопрос «верно / неверно» создать нельзя, преподаватель вынужден писать:

```
option_a = "To'g'ri"
option_b = "Noto'g'ri"
option_c = "-"      ← заглушка
option_d = "-"      ← заглушка
```

Дальше сразу две беды: перемешивание **покажет заглушки студенту как настоящие варианты**
(он увидит четыре кнопки), и две заглушки имеют одинаковый текст — получаем случай 1.

### Случай 3: узбекские апострофы — самая коварная

В узбекской латинице `o'` и `g'` пишутся с апострофом, и это **минимум четыре разных символа**:

| Символ | Код | Откуда |
|---|---|---|
| `'` | U+0027 | обычная клавиатура |
| `ʻ` | U+02BB | официальный узбекский стандарт |
| `'` | U+2018 | автозамена Word/Excel |
| `'` | U+2019 | автозамена Word/Excel |

Для человека — одна буква. Для `==` — четыре разные строки.

У проекта есть **загрузка вопросов из Excel** (`question/repository.py::upload_questions_excel`),
а Excel по умолчанию заменяет прямые апострофы на «умные кавычки». Плюс редактор jodit тоже
может нормализовать текст.

Достаточно, чтобы вариант попал в базу с одним символом, а до сравнения дошёл с другим — и
**правильный ответ засчитается как неправильный**. Диагностировать почти невозможно: на экране
оба текста выглядят идентично, разница только в невидимом коде символа.

### Случай 4: HTML внутри вариантов

Варианты отображаются как HTML (`dangerouslySetInnerHTML`). Значит внутри может быть `<p>`,
`&nbsp;`, `<img>`, форматирование из редактора. Вся разметка гоняется по сети при каждом ответе
и участвует в посимвольном сравнении.

### Случай 5: картинки и формулы — почему нынешняя схема их не выдержит

С картинкой внутри варианта текст выглядит так:

```
<p>Ответ: <img src="https://lms.nsumt.uz/uploads/question/a3f2-91bc.jpg" style="width: 200px;"></p>
```

Достаточно, чтобы редактор пересохранил `style="width:200px"` вместо `style="width: 200px;"`,
поменял порядок атрибутов или добавил пробел — и ответ не совпадёт.

С формулами то же самое: `$x^2$` и `$x^{2}$` визуально одинаковы, а как строки различны.
Одна и та же формула в MathML записывается несколькими способами с одинаковым видом на экране.

**Вывод: богатое содержимое вопросов несовместимо со сравнением по тексту.**

## Часть 3. Что невозможно построить на четырёх колонках

| Что хотелось бы | Почему нельзя |
|---|---|
| Вопрос с 2–3 вариантами | Все четыре обязательны, лишние видны студенту |
| Вопрос с 5–6 вариантами | Колонок ровно четыре |
| Несколько правильных ответов | `correct_option` — **одна буква** |
| Открытый вопрос («введите ответ») | Нет места для эталона |
| Сопоставление, упорядочивание | Структуры нет |
| Вес балла (сложный вопрос = 3 балла) | Все вопросы равны, оценка = процент верных |
| Уровень сложности | Нет поля — нельзя собрать «5 лёгких + 3 сложных», выборка случайная |
| Картинка как часть структуры | Только через `<img>` в HTML-тексте: нельзя проверить наличие, нельзя массово поменять адреса |

Пороги оценок 86/72/56 зашиты в код (`quiz_process/repository.py`). Пока все вопросы
равнозначны, иначе и быть не может.

### Контраст: психологический модуль устроен правильно

Тот же тип задачи там решён через JSONB, и у каждого варианта есть **`value`** —
опознавательный знак. Клиент отправляет `value`, а не текст, поэтому случаи 1, 3, 4 и 5
там невозможны по построению. Типов вопросов шесть: `text`, `true_false`, `scale`,
`image_stimulus`, `image_choice`, `multi_choice`.

То есть **более новый и менее ответственный модуль устроен грамотнее основного**. Это не пробел
в знаниях команды — квиз просто написан раньше и с тех пор не переделывался.

## Часть 4. Решение по модели вопроса

### Заплатка: отправлять номер варианта (делать первой)

Клиент отправляет «выбрал вариант №2», а не текст. Порядок перемешивания сервер сохраняет
при старте попытки — строки `UserAnswers` для этого уже создаются, туда добавляется одно поле
вроде `"cadb"`.

Что даёт:

- содержимое варианта становится **полностью неважным** — хоть картинка, хоть формула,
  хоть килобайт HTML; сервер сравнивает число с числом;
- исчезают случаи 1, 3, 4, 5;
- миграция маленькая, ломать ничего не нужно;
- не мешает полному переходу позже — сравнение по номеру останется и в новой модели.

**Это предварительное условие для картинок и формул, а не улучшение.** В обратном порядке
получится система, которая иногда неправильно оценивает студентов, и причину найти будет
крайне трудно.

### Полное решение: JSONB как в психологии

Варианты переводятся в JSONB со своим `value`. Открывает множественный выбор, произвольное
число вариантов, веса, уровни сложности, новые типы вопросов.

Большая работа: миграция существующих вопросов, формы создания, Excel-импорт, отображение,
отчёты. Делается после заплатки, не вместо неё.

## Часть 5. Картинки

### Решено: хранить относительные адреса

Сейчас `question/repository.py::upload_image` возвращает **абсолютный URL**:

```
f"{settings.file_url.http}/question/{filename}"
```

В текущих настройках это `http://localhost:3000/uploads` локально и `https://lms.nsumt.uz/uploads`
в примере конфигурации. Адрес попадает внутрь HTML вопроса и **остаётся в базе навсегда**.

Последствия:

- домены системы уже менялись — вопросы, созданные раньше, содержат старый домен, и если он
  перестанет работать, картинки исчезнут разом;
- вопрос, созданный на машине разработчика, вечно ссылается на `localhost:3000`;
- `http://` внутри страницы на `https://` браузер блокирует как небезопасное содержимое.

**Правильно:** хранить `/uploads/question/a3f2-91bc.jpg`.

**Уточнение: преобразовывать в абсолютный при выводе не нужно.** nginx проксирует `/uploads/`
на бэкенд с того же домена, поэтому браузер подставит домен сам. Преобразование нужно только
там, где HTML читает не браузер (экспорт в Excel, PDF, почта) — точечно в этих местах.

**Отдельная задача: разовый скрипт** для уже накопленных вопросов. В базе, вероятно, разные
домены (`lms.nsumt.uz`, прежние `test.*`, нынешние `organization.*`, `localhost:3000`) —
скрипт должен обрезать всё до `/uploads/...` независимо от домена. Делать до того,
как картинок станет намного больше.

### Решено: добавить валидацию загрузки

Сейчас `upload_image` берёт расширение прямо из присланного имени файла и сохраняет что угодно:

- нет проверки, что это изображение;
- нет ограничения размера — можно заполнить диск;
- `.svg` может содержать исполняемый код, и при открытии адреса напрямую он выполнится
  **в вашем домене**;
- если в имени нет точки, расширением станет всё имя целиком.

Добавить: проверку по содержимому (а не по имени), лимит размера, белый список типов,
безопасное имя файла, блокировку `.svg` либо отдачу его без исполнения.

### Удаление картинок: сразу удалять НЕЛЬЗЯ

Замечание верное и подтверждается кодом: **вопросы никогда не удаляются физически**.
В `question/repository.py` есть только пометки — `is_active = False` (строка ~220) и
`is_latest = False` (строка ~178). Ни одного `session.delete` для вопросов в модуле нет.

Почему это важно:

**Правка вопроса не изменяет строку — она создаёт новую версию.** Убрал преподаватель картинку:

- создаётся **новая** версия без картинки;
- **старая** остаётся в базе вместе со ссылкой на картинку;
- на старую ссылаются `UserAnswers` студентов, отвечавших раньше.

Удалив файл, вы сломаете просмотр прошлых результатов. А смысл версионирования именно в том,
чтобы история отображалась **в точности такой, какой её видел студент**.

**Как правильно.** Файл удаляется, только когда на него не ссылается ни одна версия вопроса —
ни активная, ни удалённая, ни старая. Два способа:

- **Периодическая уборка** (раз в неделю): собрать все ссылки из текстов всех вопросов, сравнить
  со списком файлов, удалить лишние. Просто, не усложняет сохранение. **Начать с этого.**
- **Учёт связей**: таблица «картинка ↔ вопрос», заполняется при сохранении. Проверка мгновенная,
  можно показать преподавателю его картинки. Требует поддержки при каждом сохранении.

**В обоих случаях — не стирать, а переносить в карантинную папку** и удалять оттуда через 30 дней.
Если уборка ошиблась, файл можно вернуть: ошибка обнаружится, когда кто-то откроет старый
результат, а это может случиться через месяц.

## Часть 6. Формулы: MathML

Решено: сейчас формулы вставляются **картинками**, нужно добавить **MathML**.

### Почему MathML подходит

- Браузеры рендерят его **сами**, без библиотек — не нужен ни KaTeX, ни MathJax.
  Фронтенд и так весит 2 МБ одним файлом, добавлять туда сотни килобайт нежелательно.
- Формула хранится **текстом**: ищется, копируется в другой вопрос, правится.
- **Word умеет отдавать формулы как MathML при копировании** — если подтвердится, задача ввода
  решается почти без разработки.

### Что сломается первым (три находки)

**1. Формулы исчезнут у студента.** В `frontend/src/pages/QuizTestPage.tsx` (строка 41):

```
DOMPurify.sanitize(html, { USE_PROFILES: { html: true } })
```

Профиль `html` **не включает MathML**. Преподаватель увидит формулу в редакторе и в списке
вопросов, а студент в тесте — **пустое место**.

Исправление: `USE_PROFILES: { html: true, mathMl: true }`. Делать **вместе** с добавлением
MathML, а не после жалоб.

**2. Очистка HTML работает только в одном месте из трёх** — отдельная проблема безопасности,
всплывшая по ходу:

| Где | Очистка |
|---|---|
| `QuizTestPage.tsx` (611, 640) — студент проходит тест | **есть** |
| `QuestionsPage.tsx` (410, 429) — список вопросов | **нет** |
| `QuestionDetailModal.tsx` (22, 41) — просмотр вопроса | **нет** |

В двух местах текст вопроса вставляется в страницу напрямую. Любой, кто может создать вопрос,
может вставить исполняемый код, и он сработает у **преподавателя или администратора** —
у пользователя с большими правами, чем автор вопроса.

При этом `.claude/CLAUDE.md` утверждает: «HTML from the backend is sanitized with DOMPurify
before rendering». Документация описывает состояние, которого нет.

**Закрыть до расширения редактора:** чем богаче редактор, тем больше HTML в вопросах
и тем незаметнее посторонняя вставка.

**3. jodit может вырезать MathML сам.** Конфигурация сейчас минимальная
(`QuestionFormPage.tsx`, строки ~83–91): только `readonly`, `placeholder`,
`insertImageAsBase64URI: false`. Разрешённые теги не заданы, применяются умолчания редактора,
рассчитанные на обычный HTML.

Проверяется за пять минут: вставить формулу, сохранить, открыть вопрос заново.

### Что проверить до начала работы

**Главное — вставка формулы из Word в jodit.** Взять реальный файл преподавателя и скопировать.
Три возможных исхода:

- **вставился MathML** — работы почти нет: разрешить MathML в очистке и в редакторе;
- **вставилась картинка** — то, что происходит сейчас; нужен отдельный способ ввода формул;
- **вставилась каша** — нужна очистка при вставке.

Результат этой бесплатной проверки определяет объём работ сильнее любых рассуждений.

**Второе — версия Chrome в аудиториях.** Браузеры рендерят MathML нативно начиная
с Chrome 109 (начало 2023). На более старых формулы отобразятся набором символов.

### Старые формулы-картинки

**Ничего с ними не делать.** Автоматически превратить картинку в MathML нельзя — это
распознавание изображений, на формулах оно ненадёжно.

Правильный путь — **сосуществование**: старые вопросы с картинками, новые с MathML.
Никакой миграции, никакого риска. Со временем картинки вытеснятся.

Ограничение: поиск по формулам и их правка работают **только для новых** вопросов.

### Где MathML не работает

Экспорт в Excel и печать в PDF — там MathML не отобразится, в отличие от картинки. В проекте
есть работа с xlsx; надо проверить, попадают ли туда тексты вопросов. Если да — для экспорта
понадобится отдельное решение, и это довод не отказываться от картинок совсем.

## Часть 7. Вставка из Word — самый частый сценарий

Преподаватели будут копировать вопросы прямо из Word. Это даёт три проблемы:

- вставляется служебная разметка Word (`mso-` стили, `<o:p>`), раздувающая текст в базе;
- картинки вставляются ссылками вида `file:///C:/Users/.../image001.png` — **такая картинка
  не откроется ни у кого, кроме автора**, и он этого не заметит, потому что у себя видит её;
- либо картинки вставляются закодированными внутрь текста — вопрос весит мегабайты
  и не проходит через `uploads` вообще.

Решается очисткой разметки при вставке и автоматическим перехватом картинок (загрузить
на сервер, подменить адрес). jodit это позволяет настроить, но **по умолчанию не делает**.
Без настройки проблема обнаружится через полгода, когда в базе будут сотни вопросов
с битыми картинками.

## Порядок работ

1. **Номера вариантов вместо текста** — предусловие для всего остального.
2. **Очистка HTML во всех местах вывода** — проблема безопасности, не ждёт.
3. **Относительные адреса картинок** + разовый скрипт для существующих вопросов.
4. **Валидация загрузки файлов.**
5. **Проверить вставку из Word** (формулы и картинки) → выбрать решение.
6. **MathML**: разрешить в DOMPurify (`mathMl: true`) и в jodit, настроить очистку при вставке.
7. **Уборка неиспользуемых картинок** с карантином.

## Попутная находка (к теме не относится, но требует решения)

У `Quiz` стоит `cascade="all, delete-orphan"` на результатах и ответах
(`backend/app/modules/quiz/model.py`), а удаление квиза выполняется физически
(`quiz/repository.py`, строка ~241).

То есть **удаление квиза стирает все результаты студентов по нему**. На фоне того, как аккуратно
защищены от удаления вопросы (только мягкое удаление и версионирование), это выглядит
несогласованно. Стоит проверить, намеренно ли так сделано.
